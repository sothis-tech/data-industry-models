# Deployment Guide

This guide describes the official procedure for a full deployment of the **Industrial Data Space** platform on a clean machine, starting only from a clone of the repository. It is written so that anyone with basic Docker knowledge can bring the stack up reproducibly, following verifiable steps without relying on implicit knowledge from the development team.

## System overview

The platform is a **monorepo** (all code vendored, no submodules) that orchestrates around **17 services** from the FIWARE and industrial-IoT ecosystem via Docker Compose. The stack integrates, among others, an Orion-LD context broker, historical persistence with QuantumLeap + CrateDB, industrial ingestion via the OPC-UA IoT Agent, a security and multitenancy layer with Keycloak + Kong, and AI components (a conversational-agent MCP server, RAG over ChromaDB, and a voice agent).

The architecture is **multitenant**: each factory data model is created under its own tenant (the `Fiware-Service` / `NGSILD-Tenant` header), so the data of each model stays isolated. Example models are `ibermot` or `metapan`; the values shown in this guide (e.g. `ibermot` in the sample commands and the IoT Agent configuration) are illustrative only and should be replaced with the tenant matching each model.

## Scope

This guide covers the full bring-up cycle: prerequisites, cloning the repository, provisioning environment variables (`.env`), host-specific adjustments, validating the Compose file, building images, starting the services, and functional validation of the stack.

**Out of scope:** the internal configuration of each microservice, development or modification of the code, and long-term production operation (scaling, backups, monitoring).

### A note on repository contents

The repository contains **sources and recipes** (Dockerfiles, `docker-compose.yml`, `*.lock` files, configuration, and `.env.example` templates), but **no secrets or heavy artifacts**. Real `.env` files, certificates, ML models, and `node_modules` / `.venv` directories are not versioned. The `.env` files are provisioned manually from the templates; everything else is regenerated by the build or downloaded at runtime.

## Prerequisites

Before starting, the target machine must meet the following requirements.

### Base software

- **Docker** and **Docker Compose v2**, installed and working. The whole deployment cycle (build, start, validation) runs through Docker Compose.
- Command-line access on a **Linux** environment (any distribution with Docker, e.g. Ubuntu) or WSL.
- **Git**, required to clone the project.
- **Outbound network connectivity**, needed to pull base images (`mongo`, `orion-ld`, `crate`, `quantumleap`, `chromadb`, `postgres`, `keycloak`, `nginx`) and, at runtime, the ML models and other non-versioned artifacts.
- **Python 3 on the host** (`python3`), required only to run the sample-data loading script during functional validation. The script uses only the Python standard library, so no extra dependencies are needed (`pip install` is not required). Unlike the service runtimes — which live inside containers — this script runs directly on the host. On most modern Linux distributions it must be invoked as `python3` (the `python` alias may not exist).

### Hardware resources (RAM and disk)

The figures below are based on measurements of the full running stack, validated across two different deployment environments. Treat them as reference values: actual consumption varies with the volume of loaded data and the selected AI provider.

**Memory (RAM).** With all 17 services up, real memory usage is around **9–11 GB**. The heaviest services are the voice agent (~2.4–3.1 GB, due to the Whisper *medium* model), the MCP server (~1.5–1.8 GB), Keycloak (~1.6 GB), the RAG manager (~1.0 GB), and Kong (~1.0 GB); the rest stay under 700 MB each.

- **Minimum:** 16 GB — the stack starts but runs at its limit and resorts to swap.
- **Recommended:** 32 GB — to operate comfortably, absorb load peaks, and leave headroom for the OS and data loading.

> If you serve a local LLM with vLLM on the same machine, memory requirements (RAM and especially VRAM) rise significantly and must be sized separately for the chosen model.

**Disk.** The bulk comes from the built Docker images, which include ML environments (PyTorch/CUDA) and are large: the conversational agent (MCP server), the RAG manager, and the voice agent each exceed 10 GB. The set of images in use is on the order of **50–55 GB**. Data volumes in their initial state are modest (~6 GB); the bulk of the disk therefore corresponds to images, not data — though volumes will grow with CrateDB/MongoDB history.

- **Minimum:** 80 GB free, accounting for images, volumes, build cache, and models downloaded at runtime.
- **Recommended:** 120 GB or more, especially if historical data growth is expected.

> During the build, Docker generates intermediate cache that can reach ~30 GB temporarily, so the disk peak during the build is higher than the final result. This cache can later be freed with `docker builder prune`.

**GPU (optional).** The stack runs entirely on CPU. An **NVIDIA GPU** is used only by the `voice-agent` service, to accelerate speech transcription with the **Whisper medium** model (ASR). The rest of the conversational intelligence (LLM via cloud provider) and speech synthesis do not depend on the GPU.

To enable GPU acceleration, the host needs:

- An **NVIDIA GPU** with working proprietary drivers (`nvidia-smi` operational).
- The **NVIDIA Container Toolkit** installed, so containers can access the GPU.
- **VRAM:** minimum **6 GB**, recommended **8 GB**. Whisper medium needs ~5 GB on GPU (FP16); the extra margin covers CUDA overhead and audio processing.

On a **host without GPU (CPU / WSL)**, remove or comment out the `deploy:` GPU-reservation block of the `voice-agent` service in `docker-compose.yml`. The service will start and run on CPU, with noticeably slower transcription (the *medium* model is demanding on CPU).

### Repository access

The project repository is **public** and hosted on GitHub (`github.com/sothis-tech/data-industry-models`). Being public, cloning requires no credentials; you only need Git installed and connectivity to GitHub.

### AI service (agent LLM)

The `mcp-server` (conversational agent) requires a language-model (LLM) provider to answer chat. The platform supports three providers, selectable by configuration:

- **Azure OpenAI** (default) — external API. Requires `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT`, and `AZURE_OPENAI_API_VERSION`. Without a valid key, the MCP server does not answer chat.
- **OpenAI Cloud** — external API. Requires `OPENAI_API_KEY`.
- **Local vLLM** — self-hosted inference server; no external connectivity needed for inference. Hardware requirements depend directly on the LLM you choose to serve and are not predefined by the platform.

If you use an external provider (Azure or OpenAI), the host needs **outbound connectivity** to the corresponding endpoint and **valid credentials**. With the local provider (vLLM), no internet egress is needed for inference, but the vLLM server must be operational.

## Deployment steps

This brings up the full stack on a clean machine, starting from a clone of the repository. The steps must be run **in order**.

### Step 1 — Clone the repository

```bash
git clone https://github.com/sothis-tech/data-industry-models.git
cd data-industry-models
```

On hosts with an old Git version, an "older Git" notice from Azure may appear; it is harmless and does not affect the clone.

### Step 2 — Provision the `.env` files

Copy each template to its `.env` and fill in the required values:

```bash
cp modelador/.env.example                          modelador/.env
cp agente_control_data_space_v2/config/.env.example agente_control_data_space_v2/config/.env
cp voice_agent/config.env.example                  voice_agent/config.env
cp voice_agent/config.dev.env.example              voice_agent/config.dev.env
```

Minimum keys for a functional stack:

- **`agente_control_data_space_v2/config/.env`** → AI provider credentials (default Azure OpenAI: `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT`, `AZURE_OPENAI_API_VERSION`). Without a valid key, the MCP server does not answer chat.
- **`modelador/.env`** → the modelador requires authentication (it is not designed to run without it). Set `ORION_AUTH_REQUIRED=true` and fill the Keycloak parameters `ORION_KEYCLOAK_REALM`, `ORION_KEYCLOAK_CLIENT_ID`, and `ORION_KEYCLOAK_CLIENT_SECRET` (see Step 7).
- **`voice_agent/*`** → tuning parameters; no mandatory secrets.

### Step 3 — Host-specific adjustments

- **Host without GPU (CPU / WSL):** in `docker-compose.yml`, service `voice-agent`, remove or comment out the `deploy:` NVIDIA GPU-reservation block.
- **Host with NVIDIA GPU:** leave the `deploy:` block as is (see GPU requirements in Prerequisites).

### Step 4 — Validate the Compose file

Resolve and validate all build paths and volumes **without building anything**:

```bash
docker compose config >/dev/null && echo "COMPOSE OK"
```

If it fails here, the most common cause is a missing `env_file` (a `.env` not copied) or an incorrect build/volume path.

### Step 5 — Build the images

Services built from the repo: `kong`, `rag-manager`, `modelador`, `mcp-server`, `voice-agent`, `iot-agent`, `opcua-linker-backend`, `opcua-linker-frontend`. The rest are pulled.

```bash
docker compose build
```

The `iot-agent` builds the `iotagent-opcua:sothis` image from `./iotagent-opcua`. On a new machine that image does not exist, so the first start must use `--build`.

> **The build can take over an hour.** Wait until it finishes completely before moving on.

### Step 6 — Start the stack

```bash
docker compose up -d
docker compose ps
docker compose logs -f --tail=50
```

The first command starts the 17 services in the background (`-d`). The next two let you check the startup state.

**Expected result:**

- `docker compose ps` should show all services `Up`. Services that define a healthcheck (`orion-ld`, `mcp-server`, `kong`, `modelador`, `iot-agent`) first appear as `health: starting` and turn `healthy` after their startup period (15–40 s). It is normal for them to take a few seconds to stabilize; wait and re-run `docker compose ps` to confirm.
- No service should stay in `Restarting` continuously or in `Exited`. A container restarting in a loop indicates a startup error (usually a bad `.env` or an unavailable dependency).
- `docker compose logs -f` should not show repeated errors or exception traces in a loop. Wait messages are expected while some services wait for others to be ready (e.g. the MCP server waiting for Orion-LD to become healthy); they disappear once the dependencies are up.

Example `docker compose ps` output with the stack correctly up (host ports and states from a recent start):


To leave the log follow (`logs -f`) without stopping the services, press `Ctrl+C`: this only interrupts the display; the containers keep running in the background.

### Step 7 — Keycloak configuration (realm and modelador client)

The `modelador` service requires authentication against Keycloak. The realm and client are configured **manually from the Keycloak admin console** once the stack is up. The resulting values are copied into `modelador/.env`.

1. Open the admin console at **http://localhost:8085**. Default admin credentials: user `admin`, password `admin_kc` (defined in `docker-compose.yml`; change them in production).
2. **Create a realm**, which is the authentication zone/space. The realm created during the Data Space project testing is **`fiware`**. Always select the `fiware` realm before configuring anything else. The modelador environment variable `ORION_KEYCLOAK_REALM` will later take this realm name (`fiware`).
3. **Within the realm, create the client** needed to request access tokens. During testing, the client **`orion-client`** was created with authentication type **OpenID Connect**. Enable **Client authentication** and **Service accounts roles**. On the final **Login settings** screen, no additional options are needed. Once created, the client appears in the **Clients** list. The variable `ORION_KEYCLOAK_CLIENT_ID` will take this client id (`orion-client`).
4. **Obtain the client secret** from the client's **Credentials** tab → this becomes `ORION_KEYCLOAK_CLIENT_SECRET`.
5. **Copy the three values into `modelador/.env`:**

```dotenv
ORION_AUTH_REQUIRED=true
ORION_KEYCLOAK_REALM=<realm-name>          # fiware, unless you created a different one
ORION_KEYCLOAK_CLIENT_ID=<client-id>       # orion-client, unless you created a different one
ORION_KEYCLOAK_CLIENT_SECRET=<client-secret>  # value obtained in the previous step
```

### Step 8 — Kong configuration (token validation)

Kong validates the JWT tokens issued by Keycloak. Its configuration is declarative and lives in `kong/kong.yml`. For a new deployment, adjust the two realm-bound values in the `jwt_secrets` section (see Step 7):

- **`key`** → the realm **issuer**, in the form `http://<keycloak-host>:8085/realms/<realm-name>`. It defaults to the `fiware` realm; replace it with the real deployment realm.
- **`rsa_public_key`** → the **RSA public key** of that Keycloak realm. The one included in the file is an example and is not valid for another realm; replace it with the key of your realm (available in the Keycloak console under **Realm settings → Keys**).

### Step 9 — Reload the services affected by configuration

Steps 7 and 8 change configuration that services only read at startup: the modelador reads its Keycloak credentials from `modelador/.env`, and Kong reads its declarative config from `kong/kong.yml`. Since the stack was already up (Step 6), both containers keep the previous configuration and must be recreated:

```bash
docker compose up -d --force-recreate kong
docker compose up -d --force-recreate modelador
```

> **Why `up -d --force-recreate` and not `docker compose restart`?** `restart` restarts the existing container without re-reading the configuration (compose, `env_file`, variables), whereas `--force-recreate` recreates it, re-reading everything. The same applies to any service whose `.env` is changed while the stack is already running.

If you prefer to restart the whole stack (e.g. after touching several `.env` files or `docker-compose.yml` itself):

```bash
docker compose down
docker compose up -d
```

> **Important:** use `docker compose down` **without** the `-v` option. `-v` removes the volumes, which would delete persistent data (among others, Keycloak's database and its realm/client configuration), forcing you to reconfigure everything from scratch.

## Functional validation

```bash
# Orion-LD alive (host 1027)
curl -s http://localhost:1027/version

# Load sample data (on Linux use python3, not python) — run from the project root.
# During testing, tenant `ibermot` was used for the ibermot example and `metapan` for metapan.
python3 examples/factory-01/load_ibermot.py --broker http://localhost:1027 --tenant ibermot
python3 examples/factory-02/load_metapan.py --broker http://localhost:1027 --tenant metapan

# context-provider serving the JSON-LD
curl -s http://localhost:8080/ -I

# iot-agent operational
curl -s http://localhost:4041/iot/about
```

Replace `<tenant>` with the tenant of the data model you want to load (e.g. `ibermot`). Then open the **modelador** at **http://localhost:8844** to start working with the data.

## Tenant access roles

For users to access the example tenants, create access roles in Keycloak. Roles are created in the **`fiware`** realm, one per tenant, in the form `tenant_<orion-ld-tenant-name>`. By default, create the role **`tenant_sdm`** for the default `sdm` tenant. Additionally, create **`tenant_ibermot`** and **`tenant_metapan`** to access the created examples.

User configuration and example execution are described in the **[User Guide](USER_GUIDE.md)**.

## Troubleshooting

Common deployment errors, with cause and solution.

| Symptom | Cause and solution |
| --- | --- |
| `docker compose config` fails with an `env_file` not found error. | A `.env` template was not copied. **Fix:** review Step 2 and copy every `.env.example` to its `.env`. |
| The `voice-agent` container restarts in a loop. Logs: `CUDA error: no kernel image is available for execution on the device`. | The image's PyTorch build lacks kernels for the host GPU architecture. Happens with very recent GPUs (RTX 50xx / Blackwell, sm_120) on PyTorch compiled for cu121 (supports up to sm_90). **Fix:** set `TORCH_VARIANT` in `Dockerfile.backend` to the value matching the GPU (`cu121` for V100/sm_70; `cu128` for RTX 50xx/Blackwell) and rebuild with `docker compose build voice-agent`. Check the architecture with `nvidia-smi --query-gpu=compute_cap --format=csv,noheader`. |
| The `mcp-server` starts but chat does not respond. Logs: `APIConnectionError` / `All connection attempts failed`. | The agent cannot reach the LLM provider. With Azure/OpenAI: missing key or no outbound connectivity. With local vLLM: the server is down, or the URL points to `localhost` from inside the container. **Fix:** verify the key in `config/.env`; for vLLM, start the server and use the Docker service name (e.g. `http://vllm:8000/v1`) or `host.docker.internal`, never `localhost`. |
| MCP server logs: `Error managing Docker: No such file or directory: 'sudo'`. | The agent tries to manage the vLLM container by running `sudo` from inside its own container, where `sudo` does not exist. **Fix:** deploy vLLM as an independent service; the agent should only connect to it over the network, not start it. |
| The modelador does not work or rejects requests. | The modelador requires authentication against Keycloak. **Fix:** complete Step 7 (create realm and client) and set `ORION_AUTH_REQUIRED=true` along with the Keycloak parameters in `modelador/.env`. |
| After regenerating the client secret in Keycloak, the modelador still fails authentication, even with the new value in `modelador/.env`. | The service reads its `.env` only at startup: a running container keeps the old secret in memory. **Fix:** after updating `ORION_KEYCLOAK_CLIENT_SECRET`, recreate the container so it re-reads the config: `docker compose up -d --force-recreate modelador`. A `docker compose restart` is not enough. |
| Kong rejects all authenticated requests (token validation error). | The `jwt_secrets` values in `kong/kong.yml` do not match the Keycloak realm: the issuer (`key`) or `rsa_public_key` belong to another realm. **Fix:** update both values (Step 8) and reload Kong with `docker compose up -d --force-recreate kong`. |
| After editing `kong/kong.yml`, changes have no effect. | Kong runs in DB-less mode and reads its declarative config at startup. **Fix:** recreate the container: `docker compose up -d --force-recreate kong`. |
| The `iot-agent` fails to start on a new machine: image `iotagent-opcua:sothis` not found. | That image is built from the repository and does not exist until the first build. **Fix:** run the full build (Step 5) or start with `docker compose up -d --build`. |
| A service fails to start: `address already in use`. | Another host process occupies one of the published ports. **Fix:** check the ports table, identify the conflict with `ss -tulpn | grep <port>`, and free or remap the port in `docker-compose.yml`. |
| The agent reports that Orion-LD is empty (0 types · 0 entities). | The broker is up but no data was loaded, or it was loaded under a different tenant than the one queried. **Fix:** load the data model with the correct tenant and verify the tenant header matches in the query. |
| After restarting the stack, the Keycloak configuration (realm, client) is lost. | `docker compose down -v` was run; `-v` removes the volumes and with them Keycloak's database. **Fix:** always use `docker compose down` without `-v`. If it already happened, redo Step 7 and update the RSA key in Kong (Step 8). |
| The build runs out of disk space. | ML images are very heavy and the build cache can reach ~30 GB. **Fix:** ensure the recommended free space and free the cache with `docker builder prune`. |
| Warning when running commands: `the attribute 'version' is obsolete`. | `docker-compose.yml` keeps the obsolete `version` attribute (Compose v2). **Fix:** harmless; remove that line to silence the warning. |
